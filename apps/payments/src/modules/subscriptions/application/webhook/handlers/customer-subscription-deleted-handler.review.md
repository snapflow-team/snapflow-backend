# Ревью: `CustomerSubscriptionDeletedHandler`

Дата ревью: 2026-05-03

## Обзор

Обработчик последовательно валидирует тип объекта, находит локальную подписку, проверяет «свежесть» события, достаёт `canceled_at`, в транзакции отменяет подписку и пишет outbox. Логика читаемая, но есть расхождения с другими webhook-хендлерами и с ожидаемым контрактом для Stripe.

---

## 1. Семантика кодов и повторные доставки Stripe

Сейчас ряд ожидаемых ситуаций мапятся на **`NotificationResultCode.InternalServerError`** с текстом `'Some error occurred'`:

- локальной подписки с таким `stripeSubId` нет;
- событие считается «старым» (`checkIsOldEvent`);
- нет `canceled_at`.

Для вебхуков Stripe обычно либо **успех без побочек** (пропуск дубликата / не наша запись), либо **явная клиентская ошибка**, чтобы не гонять бесконечные ретраи на 5xx. В проекте **`InvoicePaymentSucceededHandler`** при отсутствии локальной подписки и при старом событии возвращает **`Notification.ok()`** — здесь обратное поведение: «старая» доставка или отсутствие строки в БД отдаётся как внутренняя ошибка. Это **несогласованно** и может **провоцировать повторные запросы от Stripe** и лишние алерты.

Имеет смысл явно разделить: что считается **skip (успех)** / **4xx** / **реальный сбой**.

---

## 2. Поле `userId` в outbox vs контракт

В payload кладётся **`customer.id`** (PK таблицы `customers`), при этом тип `SubscriptionCancelledEvent` называет поле `userId` — по смыслу это обычно **идентификатор пользователя приложения** (`Customer.userId`), а не PK строки `customers`. В других сценариях (например, активация подписки) в outbox ожидают именно пользовательский `userId`.

Риск: потребители outbox трактуют поле как user id приложения и получают неверные данные.

---

## 3. `Notification.fail` внутри `prisma.$transaction`

Внутри колбэка транзакции при ошибочных ветках выполняется **`return Notification.fail(...)`** без **`throw`**. В связке Nest + Prisma это **не откатывает транзакцию** и **не пробрасывает ошибку наружу**. Метод при этом завершается **`return Notification.ok()`** после `await $transaction`, то есть возможна ситуация: **часть изменений закоммичена, outbox не записан, а снаружи — успех**. Аналогичная проблема зафиксирована для другого хендлера в интеграционных тестах.

---

## 4. Избыточность вокруг ID подписки

Используется **`extractSubscriptionId(payload.id)`**. У объекта Stripe `subscription` поле **`id` уже строка**; `extractSubscriptionId` семантически рассчитан на «ссылку» на подписку (`string | Stripe.Subscription`). Поведение корректное, но чтение кода усложняется — достаточно явного **`payload.id`** после type-guard.

---

## 5. Мелочи

- Лог: «This subscription **have** no» — грамматически лучше **«has»**.
- Сообщение `'Some error occurred'` почти не помогает в диагностике (контекст частично есть только в логах).
- **`extractCancelledAt`**: значение `0` трактуется как отсутствие (`!canceledAt`) — краевой случай, для Stripe маловероятен.
